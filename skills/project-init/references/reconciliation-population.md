# Reconciliation Population Rules

Use this reference after source-of-truth detection and before proposing missing
Markdown documents. Population is a documentation operation; it does not
implement application behavior or rewrite an existing source by default.

## Evidence levels

Every populated statement must be labelled or placed in the correct section:

- **Confirmed:** directly stated by the user or directly supported by safe,
  relevant project evidence such as a manifest, command configuration, or
  existing document.
- **Inferred:** a cautious interpretation of multiple confirmed signals; show
  the evidence and keep it separate from confirmed requirements.
- **Recommended:** an option suggested for review, never a selected decision.
- **Assumed:** a temporary value needed to make a draft readable; identify the
  assumption and do not use it to authorize implementation.
- **Unknown:** not present in the evidence or intentionally deferred.

Do not infer secrets, user identities, authorization, business rules, schema
constraints, API contracts, or deployment requirements from filenames or
framework conventions.

## Evidence-to-document mapping

Use confidence for the strength of the evidence, separately from the content
label above:

- **Direct user statement** — Confidence: High. Use for a confirmed goal,
  outcome, or behavior. Ownership: user approval.
- **Existing approved document** — Confidence: High. Preserve it or trace a
  compatible missing field. Ownership: existing owner; revise only after
  approval.
- **Manifest, lockfile, or verified config** — Confidence: high for current
  tooling. Use as operational evidence. Ownership: project owner; do not infer
  future selection.
- **Observed source behavior** — Confidence: medium/high for current behavior.
  Use for compatibility and current-state notes. It creates no new requirement
  by itself.
- **Filename or directory convention** — Confidence: low/medium. Use for
  candidate discovery only; report the candidate and never choose silently.
- **Framework or community convention** — Confidence: low. Use only as a
  recommendation or open question routed to technical comparison.
- **`.env` or secret-like path** — Confidence: none for content. Record only a
  name-level classification and exclude it from document content.

For each populated field, record the evidence path or user statement, confidence,
content label, target document/section, and generator or owner. A source file
generated by a known template or generator is updated through that generator;
do not edit its output directly. If ownership is unknown, record an open
decision and preserve the existing output.

## Missing-document procedure

1. Select the existing source-of-truth path for each document group. Preserve
   its name and location when one exists.
2. Propose only missing documents after the source scan. List the template,
   evidence sources, fields that will be populated, and fields that will remain
   open.
3. Copy the approved template with copy-if-missing behavior. Do not read or
   copy `.env`, credentials, keys, browser state, or secret values.
4. Populate confirmed safe facts and preserve the template's status and review
   gates. Place inferences, recommendations, assumptions, and unknowns in the
   matching sections.
5. If a missing document depends on an unresolved decision, create a clearly
   labelled draft only after approval; do not fabricate the decision.
6. Report evidence-to-field mappings and stop for foundational-document review.
   The user must review the populated direction, user flow, architecture, and
   baseline schema when applicable before feature candidates, SPEC, PLAN,
   migration, API, frontend, or application implementation work. Resume the
   feature lifecycle only after that review is complete.

## Document-specific boundaries

- `MASTER_PLAN.md`: product direction, outcomes, proposed scope, non-goals,
  assumptions, and open questions. Do not invent features or priorities.
- `docs/USER_FLOW.md`: confirmed and proposed actors, journeys, permissions,
  states, validation, failure, and recovery. Keep it technology-neutral.
- `docs/DB_SCHEMA.md`: only after persistence approval and user-flow review;
  record confirmed or explicitly proposed data design, access style, and
  migration decisions. Do not create migrations or models.
- `docs/PROJECT_ARCHITECTURE.md`: safe architecture evidence and open choices;
  do not turn framework detection into approval of the future design.
- `AGENTS.md`: operational commands, validation, source layout, security,
  generated-file ownership, and routing. Never place secrets or invent
  commands that were not confirmed or verified.
